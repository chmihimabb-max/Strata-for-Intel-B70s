D2c (t_c7d8cd86): the other 61 decode-path programs are built in the load phase too - and what that is worth

D2b moved the dense (type x ncols) MMVQ family out of the first decode windows. A cold 4K first run
still built 61 programs inside its decode phase: 55 one-off kernel SITES plus the 6 routed-expert
native_gu_multi_kernel<T>/native_down_multi_kernel<T>. D2b's name_other.py saw "(no symbol)" for 35 of
them; they are all nameable from the mangled typeinfo in each cache entry's SPIR-V, and
d2c/enumerate_c.py names every one with its launch site and kernel instantiation (d2c/ENUMERATION.txt).

This adds the same treatment for the warmable part of that set - decode_warmup() in
src/kernels/cuda/decode_warmup.cu, called from the serve path right after native_mmvq_warmup and still
before "everything loaded", on the caller's stream over a zeroed scratch arena it allocates itself, with
STRATA_KERNEL_WARMUP=0 as its own A/B arm (separate from STRATA_MMVQ_WARMUP). 54 launches over 54 sites;
no kernel source, no config and no default is touched.

Measured (4K, 256 new tokens, both caches fresh = a fresh install):

  warm-ups      programs in the ask     residual          load    ask      start -> first answer
  none          152  (59 + 93 decode)   128.26 ms/win     32 s    33.28 s  65.28 s
  D2b's only    112  (51 + 61)           35.51             49 s    28.23 s  77.23 s
  both          66   (51 + 15)            9.46             52 s    26.20 s  78.20 s

So the pass removes 46 of the 61 programs and 1407 ms of the 1918 ms residual, and it does NOT turn the
trade-off positive: +2.29 s of load against -2.03 s of ask. The card's premise does not survive the
measurement - the 61 programs are one per SITE, so a request needs all of them and warming them moves
work rather than removing it. The 12.9 s a fresh install still pays is D2b's over-warm (96
specializations built where a 4K request uses 32); the lever is fewer programs, not earlier ones.
What the pass buys is the first request (93 -> 15 programs built in its decode windows, 6.9 -> 0.5 s of
in-request compiler time) and it costs 5 ms on every later request.

Every arm, cold or warm, reproduces the canonical ids (4K 66bf952d445e330c974c49e4f220b4b1, 32K
d87373e84417dab60732a95eb47666a6); ctest -R mmvq_multi_parity passes, the warmed kernels' families are
12 passed of 16 and the S4 set is 5 failed of 49 - the same five names as the recorded baseline.
