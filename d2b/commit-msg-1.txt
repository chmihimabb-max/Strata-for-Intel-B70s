D2b (t_f93760a1): the decode path's (type x ncols) specializations are built inside the first decode windows - build them in the load phase

D2a measured the mechanism behind D2's 60% window-cost spread; it could not measure the case a user meets,
because every arm it ran had its programs already built.  This card measures a cold first run of the SHIPPED
layout and then moves the build out of the measured window.

1. THE USER-VISIBLE CASE.  Both SYCL_CACHE_DIR and NEO_CACHE_DIR empty (a fresh install; the shared warm caches
   were never moved - the cold arms point both variables at fresh /tmp dirs instead), 4K, the config of record's
   flags with --spec-min-p 0.7: 153 SYCL programs are built while the ask is in flight, 32 of them the dense
   native_mmvq (type x ncols) family, and the part of verify no counter owns is 127.93 ms/window x 54 windows =
   6908 ms - 83% of that run's total window time (its warm control: 3.56 ms/window, 0 programs).  The same cold
   run still produces the shipped canonical ids 66bf952d...: the shipped layout's numbers do not depend on the
   window size, so the cost never was the cause of the ids.

2. THE FIX.  native_mmvq_warmup() (src/kernels/cuda/native_mmvq.cu), called once from the serve path of
   generate.cpp immediately before "everything loaded": for each of the six quantization types the config of
   record's decode path reaches (Q4_K, Q5_K, Q6_K, IQ4_XS, IQ4_NL per d2/D2-TYPES.txt, plus the MTP drafter's
   Q8_0) and ncols 1..8 it launches TWO input sizes per type - one below and one above the
   `n_in / F::DIV < F::BPI` crossing, so both runtime launch shapes are built.  192 launches over scratch buffers
   of its own, with an all-zero activation: nothing it computes is read, and the ids check is the evidence for
   that rather than the argument.  STRATA_MMVQ_WARMUP=0 is the A/B arm; the default is on.

3. WHAT IT BUYS.  The cold decode phase then builds 61 programs and 0 mmvq (it was 93 with 32 mmvq), the
   residual falls to 36.27 ms/window = 1959 ms, the decode wall 13696 -> 8587 ms (10.7 -> 17.1 tok/s) and the
   ask 33.77 -> 28.22 s.  Warm the residual stays at the shipped level: 2.50 ms/window with the warm-up on,
   2.85 ms with it off, 3.56 ms on the pre-fix binary at 4K, and 1.38 ms at 32K.

4. WHAT IT COSTS.  17538 ms on a fully cold first run (load wall 31 -> 49 s), 7298 ms in a session where the
   dense programs were only partly cached, 41 ms once they exist (load wall back to the shipped 32 s).  On a
   fresh install the first REQUEST is 5.5 s faster but the first ANSWER arrives 12.4 s later, because the warm-up
   builds ~60 programs the request may never need while 61 other decode-path programs (6 routed-expert gu/down
   and 55 one-off kernels - bf16 mmvf, quantize_q8_0_scaled, gdn_*, qsa attn_chunk/block_scores, mtp_select,
   sampler_greedy, ...) still build inside the request either way.  That second family, and the payback it would
   give on the fresh-install total, is follow-up card t_c7d8cd86 (see d2b/STATUS-D2B.md section 8).

5. THE CHECKS.  ids: 4K 66bf952d445e330c974c49e4f220b4b1 (147 tokens) and 32K d87373e84417dab60732a95eb47666a6
   (256 tokens) in all seven arms - both cold arms, both warm-up-on arms, the warm-up-off control, the pre-fix
   binary's arms.  ctest -R mmvq_multi_parity: 1/1 passed.  The S4 ctest set: 5 failed of 49, the same five names
   as the recorded baseline (platform_memory_test, elementwise_parity, quantize_act_parity, iq_multi_parity,
   expert_multi_test).
